### Q1. Why is a commit history useful when maintaining software?
A commit history provides a chronological audit trail of every saved snapshot, recording who made each change, when it happened, and why. During software maintenance, this history is essential for isolating exactly when a bug or configuration error was introduced so developers can inspect the diff or revert to a known working state. For example, in my local repository, I made distinct, incremental commits such as "Add README for SCM evidence repository", "Add student name to README", and "Add .gitignore". If an accidental edit in README.md broke documentation formatting or exposed sensitive files because .gitignore was misconfigured, I could run git log --oneline to pinpoint the exact commit and restore the stable version without losing the rest of my project work.   
### Q2. Explain the difference between Git and GitHub, using your two repositories as examples.
Git is the distributed version control program that runs locally on my computer via the command line to track file changes, manage branches, and record commits. GitHub is an online cloud hosting service for Git repositories that adds web-based collaboration features such as pull requests, issues, and automated GitHub Actions workflows. In Part 2, my GitHub Skills exercise repository lived and was operated entirely on GitHub's web interface, where an automated bot guided me through branching and merging in the browser. In contrast, I created the scm-lab-evidence repository locally on my computer using git init in the terminal, recorded several commits offline, and only later used git push to publish that history to GitHub as a remote backup and collaboration point.   
### Q3. In the GitHub Skills exercise you worked on a branch and used a pull request instead of changing main directly. What risk does this reduce?
Working on a separate feature branch and opening a pull request reduces the risk of introducing untested, broken, or conflicting code directly into the production-ready main branch. Because the main branch usually represents the stable version of the software that the rest of the team relies on, committing directly to it can disrupt everyone's work if a change contains an error. By isolating changes on a separate branch first, developers can experiment safely without affecting the main codebase. Opening a pull request then creates a dedicated checkpoint where teammates and automated checks (like GitHub Actions) can review, discuss, and verify the changes before they are merged into main.   
### Q4. State which of your commands changed only your computer and which changed GitHub.
Almost all of the Git commands I ran—including git init, git add, git commit, git switch -c, git merge, git branch -d, git restore, and git remote add origin—changed only the files and local .git repository on my own computer. Even git clone and git pull only read data from GitHub and modified the files and commit history on my local machine. The only command that actually changed the repository hosted on GitHub was git push (and git push -u origin main), which uploaded my locally recorded commits from my computer to the remote server.
